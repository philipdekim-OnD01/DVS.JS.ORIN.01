# Jetson .121 FPS 측정과 증속 검토 — 2026-11-02

설정창 적용 커밋 `3ff3c41fb5cdf91450b4761095c66774acd990ff`의 실행본을
SSH로 조회했다. 이 작업에서는 센서 레지스터, 프리뷰, 전력 모드 또는 클럭을 변경하지 않았다.
측정값은 [터미널 출력에서 보존한 JSON](evidence/2026-11-02/fps-measurement.json)에 있다.

## 현재 속도

`/stats.json`을 약 1초 간격으로 5번 읽고, 첫 표본과 마지막 표본의 카운터 차이를
호스트 monotonic 시간 차이 **4.003초**로 나눴다. 센서 후보 timestamp를 시간 기준으로
사용하지 않았다. 측정 중 capture PID는 `67942`, 상태는 `live`였다.

| 항목 | 측정값 |
|---|---:|
| RAW2 디코딩 프레임 | 1,597.80프레임/초 |
| VI 수신 버퍼 | 1,596.55버퍼/초 |
| 수신 데이터 | 267.49MiB/s |
| 해석한 이벤트 | 약 652,410개/초 |
| 서버가 생성한 표시 프리뷰 | 58.71프레임/초 |
| 설정된 프리뷰 합성 간격 | 16,666µs, 목표 약 60fps |
| 수신 누락 / 드라이버 버퍼 고갈 / 오류 버퍼 | 모두 0 |
| 원본 파이프 누락 / 화면 파이프 생략 | 모두 0 |

여기서 약 1,600fps는 **DVS RAW2 데이터의 디코딩 프레임 속도**다.
일반 RGB 카메라의 노출 영상 FPS나 이벤트 개수/초와 구분한다.
VI 버퍼와 디코딩 프레임은 다른 카운터이므로 두 비율이 정확히 같을 필요는 없다.
58.71fps는 서버 프리뷰 생성 속도이며, 브라우저 실제 그리기 속도를 측정한 값은 아니다.

센서 시각 후보의 간격은 다섯 표본 모두 `624µs`였다. 그러나 RAW2 후보 시각의
물리적 의미는 아직 교정되지 않았으며, 측정 끝의 누적 시각 모호성은 `199`,
후보 역행/동일은 `15`였다. 따라서 센서 시각만으로 정확한 광학 시간 해상도를 보증하지 않는다.

## 현재 속도가 정해지는 이유

1. **표시 프리뷰:** `app/dvs_streamer/src/main.cpp`의 기본 `preview_us`는
   `1'000'000 / 60`이다. 현재 RAW2 프레임 약 27개를 한 화면으로 합친다.
2. **센서 수신:** 현재 `Delta_10_2000FPS_RAW2.txt` 설정으로 약 1,600fps가 들어온다.
   이 파일 자체에도 파일명은 호환용이며 2,000fps 보장이 아니라는 주석이 있다.
3. **원인 판단의 한계:** 입력과 해석 속도가 같은 범위이고 누락 카운터가 0이므로,
   디코더 처리 실패로 1,600fps에 제한된다는 증거는 없다. 하지만 이것이 2,000fps에서의
   처리 여유를 증명하지는 않는다. 정확한 센서 주기는 실제 외부 클럭, PLL, 스캔 타이밍,
   패킷·프레임 간격의 조합을 확인해야 한다.

드라이버는 setfile의 레지스터 목록을 센서에 적용한다. 보드는 별도 발진기를 사용하고
CAM1_MCLK를 요청하지 않는다. DT의 `mclk_khz`나 `pix_clk_hz`만 보고 실제 센서 클럭을
측정한 것으로 간주하면 안 된다. DT/드라이버의 V4L2 모드 표에 있는 `30fps`도
이번 실측 RAW2 수신 속도와 구분한다.

## 더 높일 수 있는 범위

**표시 프리뷰:** 설정창의 프리뷰 합성 메뉴에 120fps가 있다. 이 선택은 센서 송출
FPS를 바꾸지 않는다. 실제 화면 갱신은 브라우저 처리량과 디스플레이 주사율에도
영향을 받는다. 이 뷰어가 사용하는 `requestAnimationFrame`의 호출 빈도는 일반적으로
디스플레이 주사율에 맞춰진다. [MDN 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

**센서 수신:** 2,000fps는 시험 목표로 검토할 수 있으나 아직 달성·안정성이 검증되지 않았다.
현재 버퍼 크기 `175,680바이트`로 2,000버퍼/초를 수신한다고 가정하면
`351,360,000바이트/초 = 335.08MiB/s`가 필요하다. 현재보다 약 25% 높은
메모리 수신량이며 CSI 프로토콜 오버헤드와 후속 복사·디코딩 비용은 별도다.

조회한 전력 모드는 `25W`였고, 짧은 tegrastats 표본에서 CPU 클럭은 `1,344MHz`,
CPU 온도는 약 `52.3~52.6°C`였다. 이 표본만으로 장시간 부하나 모든 스로틀링을
배제할 수 없다. NVIDIA의 전력/클럭 도구는 처리 성능과 전력 정책을 조정하는 도구이며,
센서 setfile의 송출 주기를 자동으로 바꾸는 기능은 아니다.
[NVIDIA Orin 전력·성능 문서](https://docs.nvidia.com/jetson/archives/r39.2/DeveloperGuide/SD/PlatformPowerAndPerformance/JetsonOrinNanoSeriesJetsonOrinNxSeriesAndJetsonAgxOrinSeries.html)

## 다음 시험 계획 — 아직 실행하지 않음

현재 약 1,600fps 설정을 보존한 별도 프로파일에서 센서 클럭·타이밍 계산을 먼저
확인한다. 근거가 확보된 설정만 적용해 목표 2,000fps를 단계적으로 시험하고,
호스트 시간 기준 프레임·버퍼 증가량, CSI 오류, 누락, 버퍼 고갈, 디코더 오류,
온도 및 녹화 처리량을 함께 비교한다. 실패하면 기존 프로파일로 복구한다.

증속 설정 변경이나 2,000fps 수신 시험은 이 기록에 포함되지 않는다.
