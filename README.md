# 현재 Jetson .117 RAW2 실행 (2026-10-16)

```bash
./build.sh app       # 현재 작업 사본의 SDK와 dvs_streamer만 함께 빌드
./dvs start         # RAW2 수신·Viewer 시작, 자동 녹화 없음
./dvs status
./dvs stop
```

기존 `python3 app/run.py start|stop|status`도 같은 실행본을 사용한다.
브라우저는 위 주소로 직접 열며, 이미 실행 중이면 `status`로 확인한다.
과거 legacy runner의 `--bind` 옵션은 지원하지 않으며 로컬망에만 화면을 제공한다.
UI 녹화 저장 위치는 현재 Viewer 기준 `app/dvs_streamer/build/GCC-arm64/Release/recordings/`다.
과거 repo 루트의 `recordings/` 및 기존 녹화 파일은 그대로 보존한다.
실행 경로는 `app/dvs_streamer/build/GCC-arm64/Release/`이며 기본 설정은
`settings/Delta_10_2000FPS_RAW2.txt`다. SDK와 앱의 동명 설정은 동일한
검증값 `3907=0F`, `3908=10`, `3915=04`를 사용한다. 파일명은 호환을 위해
유지하며 실제 속도는 약1600fps다. 화면은 `http://192.168.0.117:8080/`에서 본다.

RAW2는 가변 embedded·BE32 화소 순서·960열 처리, 표시용 monotonic 시각,
디코딩 worker와 RAW 큐512를 사용한다. Group AER는 기존 decoder/입력 큐1을
유지하며 명시적 `--settings`로 선택한다. UI 녹화는 기존 zstd 경로이므로
수신 시작만으로 녹화를 시작하지 않는다. 간헐 VI 수신 오류는 아직 미해결이다.

기존 `build/dvs_live`와 `app/dvs_live`는 아래 과거 배포의 실행 경로다.
이번 통합에서 사용하지 않으며 보존용 백업으로 옮긴다. driver/DT/boot와
자동부팅 서비스는 바꾸지 않는다. `compression_bench`는 빌드·실행 대상에서 제외한다.

아래는 원래 드라이버/BSP 배포 문서다. 과거 앱 실행·빌드 설명보다 위 절을 우선한다.

# nrv-dvs-jetson

Distribution source tree for the NRV DVS camera (CAM1) on Jetson Orin Nano Super
(P3768 + P3767-0005), NVIDIA Jetson Linux **R39.2.1**, kernel `6.8.12-1021-tegra`.

It uses NVIDIA's camera stack **unmodified** (the sensor sends CSI-2 RAW8 `0x2A`,
which stock VI accepts), ships the sensor wiring as a **device-tree overlay**
(`cam1.dtbo`, intended to be applied by the bootloader through an extlinux
`OVERLAYS` line), and contains the sensor driver and the receiver app.

> Verification status of this tree: built and checked offline only.
> **NOT loaded, NOT booted, NOT receive-tested.**

## Layout

| Path | Content |
|---|---|
| `build.sh` | `fetch \| drivers \| compdb \| dt \| app \| all \| clean` (build only, never installs) |
| `drivers/dvs/.clangd`, `.vscode/settings.json` | clangd uses `drivers/dvs/build/compile_commands.json` (generated) |
| `bsp/r39.2.1/manifest.env` | source URL, SHA-256 pins, kernel release, Module.symvers pins, BSP version |
| `drivers/dvs/` | `src/`, `include/`, `Makefile` (no sensor configuration inside; see "Sensor register control") (declares the driver's build deps; `make` in `drivers/dvs` builds only the driver into `drivers/dvs/build`, `build.sh drivers` builds it into `build/dvs`; needs `build/compat` from one `build.sh drivers`) |
| `device-tree/p3768-cam1/cam1.dts` | overlay source (`/plugin/`) |
| `config/` | setfiles: `Delta_10_2000FPS.txt` (preset, app default), `Delta_10_2000FPS_EvthMax.txt` (same with maximum event sensitivity) |
| `sdk/` | user-space C++ SDK (`libnrv_dvs`): Device (register list), Stream, Pipe, Decoder; `sdk/tests` has the stress test |
| `app/`, `dvs` | receiver (`dvs_live.cpp <setfile>`: sends the setfile as the register list, then SDK Stream -> DropPipe -> Decoder -> DropPipe -> stdout), web viewer (reads it on stdin, serves the latest 2-bit frame on `/frame`, which the page requests again after each draw), desktop viewer, launcher |
| `boot/extlinux-entry.example` | reference of the entry generated by `scripts/boot-setup.sh install` |
| `scripts/boot-setup.sh` | `check \| install \| status \| uninstall`: B-2 boot activation (see below) |
| `docs/OPEN-ISSUES.md` | open review items (deskew, boot/runtime verification) |
| `tests/` | `check-build.sh` and Python helpers (offline acceptance checks) |
| `.cache/`, `build/` | git-ignored: verified NVIDIA downloads, build outputs |

## Build (on the Jetson)

```bash
./build.sh all            # fetch + verify + nrv_dvs.ko + cam1.dtbo + dvs_streamer
./tests/check-build.sh    # offline acceptance checks
```

Outputs: `build/nrv_dvs.ko`, `build/cam1.dtbo`,
`app/dvs_streamer/build/GCC-arm64/Release/dvs_streamer`.

`drivers` also writes `drivers/dvs/build/compile_commands.json` (git-ignored;
regenerate alone with `./build.sh compdb`); `drivers/dvs/.clangd` points clangd
there (`CompileFlags.CompilationDatabase`) and removes GCC-only flags. It is produced by the kernel's
`scripts/clang-tools/gen_compile_commands.py` from the real build commands of the
module: `drivers/dvs/src/*.c` entries point at the source in this repo. Paths are absolute device
paths (kernel headers under `/usr/src/linux-headers-*`), so open the folder on the
Jetson, e.g. with VS Code Remote-SSH + the clangd extension (it downloads clangd if
none is installed; the board has none).

`fetch` downloads `public_sources.tbz2` from NVIDIA (URL in the manifest, ~310 MB),
verifies its SHA-256, extracts only `kernel_oot_modules_src.tbz2`, verifies that
pin, validates tar member paths and extracts `nvidia-oot` to `.cache/pristine/`.
A bad cached file is never accepted silently. `NRV_PUBLIC_SOURCES_ARCHIVE=<file>`
uses a local copy of the official archive (still hash-verified).

Only NVIDIA's conftest scripts are used from these sources: `drivers` generates the
conftest headers the sensor driver needs with NVIDIA's own conftest Makefile into
`build/compat/`. No NVIDIA module is rebuilt or changed.

Preflight refuses to build unless the machine is aarch64, runs the pinned kernel,
and `Module.symvers` (kernel and `/usr/src/nvidia/nvidia-public`) plus the
`nvidia-l4t-core` version match the manifest. The modules are therefore
**BSP-locked** to R39.2.1 / `6.8.12-1021-tegra`.

Known warning: the installed GCC is 13.3 while the kernel was built with GCC 13.2;
`IGNORE_CC_MISMATCH=1` is set for the conftest step to acknowledge this. It does
not prove runtime ABI safety. Modules are unsigned.

## CSI-2 data type: RAW8 (0x2A), no NVIDIA patch

Stock VI matches only the data type implied by the pixel format (RAW8 -> `0x2A`,
RAW10 -> `0x2B`, ...); every DT mode here is SRGGB8, so VI takes `0x2A` packets
and stores their payload bytes unchanged. Every setfile therefore writes
`3901=2A`. The sensor's reset default is the user-defined data type `0x31`, which
stock VI silently drops (capture timeout, no frames) — a setfile without
`3901=2A` does not stream. The data type is only a packet label: the payload
format is selected by `0x3260` bit1 (0 = group AER, 1 = RAW2), and the SDK picks
the decoder from that register, never from the data type. (Earlier trees matched
`0x31` through a VI patch; it was removed, see `docs/OPEN-ISSUES.md` item 7.)

## Sensor register control (`nrv_register_writes`)

`nrv_dvs.ko` has **no module parameters and no built-in sensor configuration**
(the driver can be published without revealing how the sensor is set up). At
every stream start (`set_mode`, i.e. STREAMON) the driver resets the sensor,
writes `0100=00`, writes the register list stored in one generic V4L2 control in
order and waits 2 ms. **With an empty list the driver refuses to stream** (`set_mode` returns
`-ENODATA`, log "register sensor settings").
The list is a setfile's `20:AAAA=VV` writes in order, without its final stream-on
`0100=01` (the driver starts streaming itself); `app/dvs_live` sends it through the
SDK (`delta::Device::SetRegisterList`). For `config/Delta_10_2000FPS.txt` (84 writes)
the bus sequence is the former built-in setfile path plus the `3901=2A` write.

| Item | Value |
|---|---|
| name | `nrv_register_writes` |
| CID | `V4L2_CID_USER_BASE + 0x2000` = **`0x00982900`** (driver-private; clear of the per-driver bases reserved in the 6.8 `v4l2-controls.h`, re-check on BSP upgrades) |
| type | `V4L2_CTRL_TYPE_U32`, flags `DYNAMIC_ARRAY \| EXECUTE_ON_WRITE` (+`HAS_PAYLOAD`), 1 dimension, max **4096** elements (16384 bytes) |
| element | native-endian u32 `(addr << 8) \| value`: bits 23:8 register address (u16), bits 7:0 value (u8), bits 31:24 must be 0. Order and duplicates are kept. |
| empty list | the single word `0xffffffff` (also the default after load). Linux 6.8 rejects zero-byte dynamic arrays, so the marker is needed; it is only valid alone and is never written. With it the driver will not stream. |
| rejected | any word for register `0x0100` (stream on/off is driver-owned) |
| on `/dev/video0` | created from the subdev `.registered` op, so VI inherits it when it binds the sensor |

Semantics:
- Setting the control only **stores** the list (validated as a whole first); no
  I2C happens. It reaches the sensor at the **next stream start**. While streaming the driver returns **`EBUSY`** (stop the receiver
  first). Reading the control returns the stored list, not sensor registers.
- `set_mode` takes a snapshot of the list before resetting the sensor; a change
  made after that point (between `set_mode` and the start write) is used at the
  following stream start. Configure the list before STREAMON.
- The list must set `0x3901=2A` (see the data type section above). Other writes
  can change the lane rate or PLL and
  then no longer match the fixed receiver timing in the DT; that is the user's
  responsibility. A failed write puts the sensor in standby and the
  stream start fails; the next start resets the sensor again.

`dvs_live <setfile>` sets the list before its stream start (no root: read/write
access to `/dev/video0`, normally the `video` group, is enough). Once the module is
loaded, `v4l2-ctl -d /dev/video0 -L` lists the control (diagnostic only).

Receiver timing is fixed in the DT mode0 node, not in the driver: `pix_clk_hz =
"1250000000"`, 4 lanes, 8 bit, DPHY, `cil_settletime = "0"` (auto), `lane_polarity
= "0"`. NVIDIA's `sensor_common.c` derives `pixel_clock` = 1.25e9 pixel/s, lane
rate = 1.25e9 x 8 / 4 = 2.5 Gbps and DPHY `mipi_clock` = 1.25 GHz. These are
receiver settings; the sensor's actual lane rate (2.5 Gbps intended by the
setfile PLL) has **not been measured**. The new driver and the new `cam1.dtbo`
must be activated together.

What is equal and what is not, compared with the removed runtime receiver-rate
parameter (2500 Mbps, applied by the old driver after probe):

- **Equal (NVCSI CIL, read at stream start):** `mipi_clock` 1.25 GHz,
  `cil_settletime` 0 (auto), `lane_polarity` 0; deskew stays off. NVCSI reads
  these from the mode at stream on, so the old runtime override and the new DT
  value end up the same.
- **Not equal (VI / `tegra_camera_platform`, read at VI bind):** VI copies
  `pixel_clock` once at bind (`tegra_channel_get_sensor_peak_vals()` ->
  `cdev->pixel_rate` / `bw` -> `tegra_camera_device_register()`). At stream on,
  `tegra_camera_platform` derives the requested NVCSI clock, VI clock and ISO
  bandwidth from that rate. In the observed baseline module reload the
  subdev was bound before the old driver applied its parameter, so this path
  saw the old DT value **500e6**. With this tree it sees **1.25e9** from bind,
  i.e. about 2.5x higher clock/bandwidth requests. This follows from the
  required `pix_clk_hz` 1.25e9 (the same value also feeds `mipi_clock`) and is
  **not tested at runtime**; see `docs/OPEN-ISSUES.md` issue 3.

## Device tree overlay

`device-tree/p3768-cam1/cam1.dts` is the validated CAM1 overlay with the sensor node
`/bus@0/i2c@3180000/nrv_dvs@10`.

Only `cam1.dtbo` is the shipped DT artifact. `tests/check-build.sh` merges it offline
(`fdtoverlay`) into the stock base DTB into `build/tests/cam1.merged.dtb` — a test
scratch file, never shipped or referenced at boot — and compares the sensor / VI /
NVCSI / tegra-camera-platform nodes with the previously validated merged DTB: the
only differences must be the sensor compatible, renamed from
the bring-up `"nrv,s5krc1s-cam1-test"` to `"nrv,fx20-sensor-board", "samsung,s5krc1s"`,
and mode0 `pix_clk_hz` `"500000000"` -> `"1250000000"` (receiver rate now in the DT;
NVCSI CIL values equal the old runtime ones, the VI bind-time pixel rate does not,
see above). The inherited `dtc` graph/unit-address
warnings are recorded in `build/logs/dtc.log`.

If the reference DTB is not present (any machine other than the validation device),
that comparison is skipped and reported as "not present" but the check still passes.
On the validation device run `REQUIRE_REF_DTB=1 ./tests/check-build.sh` so a missing
reference DTB fails the check instead.

The overlay has no `overlay-name` / `jetson-header-name` properties (the stock
`/boot/*.dtbo` files have them). They are not needed for an extlinux `OVERLAYS`
line; add them only if the overlay should be listed by Jetson-IO.

## Boot activation: `scripts/boot-setup.sh` (path B-2)

`build.sh` never installs. Activation is done by `scripts/boot-setup.sh`, followed
by a reboot:

```bash
./build.sh all
scripts/boot-setup.sh check              # read-only preflight
sudo scripts/boot-setup.sh install       # --dry-run shows every change first
sudo reboot
scripts/boot-setup.sh status             # overlay applied? loaded .ko == build/?
./dvs                                    # receive test (starts receiver + web, opens the browser)
sudo scripts/boot-setup.sh uninstall     # undo everything install added, reboot
```

What `install` does (and only this):
- copies `build/nrv_dvs.ko` to `/lib/modules/$K/updates/nrv/` and removes a
  `tegra-camera.ko` an older install left there (the NVIDIA camera stack stays
  stock);
- writes `/etc/depmod.d/nrv-dvs.conf` (`override nrv_dvs $K updates/nrv`) and runs
  `depmod -a $K`. The override must use the module **file** name. Without an
  override, which `updates/` copy wins depends on directory names. NVIDIA uses
  the same mechanism for its display driver (`updates/opensrc-disp`);
- copies `cam1.dtbo` to `/boot/nrv-dvs/` (nothing is added to `/boot/dtb`: NVIDIA's
  kernel-dtbs postinst and Jetson-IO assume a single `.dtb` there);
- backs up `extlinux.conf` to `/boot/nrv-dvs/backup/`, adds/refreshes the `nrv-dvs`
  entry (see `boot/extlinux-entry.example`) and makes it `DEFAULT`.

Notes:
- **`FDT` is required for `OVERLAYS`.** L4TLauncher applies overlays only while
  loading the `FDT` file; without `FDT` the overlay is silently ignored. The base
  DTB is detected at install time (single `/boot/dtb/kernel_*.dtb` matching
  `/proc/device-tree/model`), never hard-coded.
- **Never hot-reload the camera stack.** `rmmod nvhost_vi5 nvhost_nvcsi nvhost_isp5
  tegra_capture_isp tegra_camera` hard-hung the board without any log (2026-10-12).
  The script never runs `rmmod`/`insmod`/`modprobe`; modules change on reboot.
- The depmod override applies to every boot entry (including `primary`), but the
  `primary` entry has no overlay, so the camera is simply absent there. After a
  kernel update (`$K` changes) the override no longer matches and the stock
  modules load (safe failure: boots, camera inactive until rebuilt).
- The stale `/lib/modules/$K/extra/nrv_dvs.ko` from the bring-up (not package-owned)
  is reported by `check` and left untouched; the override makes `updates/nrv` win.
- Receive with the stock camera stack and `3901=2A` group AER is **not yet
  verified** (RAW2 already ran with `0x2A`).

## Runtime app (not exercised by the build/tests)

`./dvs` starts the receiver and web server if they are not running (and then starts
recording with the defaults: no rotation, 4 GiB files) and opens
`http://127.0.0.1:8080/` in the browser (the previous multi-command script is kept as
`dvs.bak`). `app/run.py start [--settings SETFILE]` (default
`config/Delta_10_2000FPS.txt`) starts `dvs_live SETFILE /dev/video0 CONTROL | viewer.py`;
`app/run.py stop|status` (or the page's stop button) stop it or print its state. Recording is started and stopped from
the web page (save folder, rotation on/off, file size, file count): the viewer writes a
command line to the control FIFO (`/dev/shm/nrv-dvs-live/control`) and dvs_live starts a
thread that writes every raw buffer through a WaitPipe (2048 buffers = 2 GiB queue; when
it is full the Stream waits) and the SDK `Compressor` (one zstd level-1 frame per buffer) to `<folder>/<date-time>/dump-NNNN.bin.zst`
(O_DIRECT; a file never splits a frame, so files decompress alone and `cat dump-*.zst |
zstd -d` gives the received stream; with rotation the oldest file is overwritten; the buffers
around a loss event go to `event-<frame>.bin.zst`) and the viewer keeps `status.yaml` (bytes/frames
written, dropped frames, driver starvation) and `events.yaml` there up to date. Runtime behavior, not part of the build or tests. The
old `/sys/module/*/parameters` checks were removed from `app/run.py` and
`scripts/boot-setup.sh status`.
